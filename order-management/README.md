# Система обробки замовлень

Простий консольний Maven-проєкт із трьома Java-модулями. Два потоки обробляють замовлення електроніки та одягу й додають успішні замовлення до спільного сховища в оперативній пам'яті.

Потрібні JDK 17 або новіший і Maven 3.9+. У IntelliJ IDEA можна користуватися вбудованим Maven. Lombok і JavaFaker завантажуються автоматично під час першої збірки, тому для неї потрібен інтернет.

## Запуск в IntelliJ IDEA

1. Розпакуй архів.
2. Відкрий кореневий файл `order-management/pom.xml` через File → Open як Maven-проєкт.
3. Вибери JDK 17 або 21 у File → Project Structure → Project SDK.
4. Дочекайся завантаження залежностей. За потреби натисни Reload All Maven Projects у вікні Maven.
5. У вікні Maven відкрий кореневий проєкт → Lifecycle → package та запусти його подвійним натисканням.
6. Відкрий `order-threads/src/main/java/com/example/order/threads/Main.java` і запусти `main` зеленою кнопкою біля методу.

Якщо IDEA підкреслює `builder()`, перезавантаж Maven-проєкт і перевір Settings → Build, Execution, Deployment → Compiler → Annotation Processors → Enable annotation processing.

## Запуск із термінала

Виконуй команди з кореневої папки `order-management`, де знаходиться головний `pom.xml`.

Збірка разом із тестами:

```text
mvn clean package
```

Запуск у Windows через CMD або PowerShell:

```text
java -Dfile.encoding=UTF-8 --module-path "order-threads/target/order-threads-1.0.0.jar;order-threads/target/lib" -m order.threads/com.example.order.threads.Main
```

Можна також запустити `run.bat`: він збере проєкт, виконає програму та залишить вікно відкритим. Для цього команди `java` і `mvn` мають бути доступні в PATH. Якщо Maven є лише всередині IntelliJ, скористайся запуском з IDEA.

У Linux і macOS:

```text
sh run.sh
```

Окремий запуск тестів:

```text
mvn test
```

## Що відбувається під час запуску

JavaFaker створює дані для п'яти замовлень електроніки та п'яти замовлень одягу. Об'єкти товарів створюються через `Electronics.builder()` і `Clothing.builder()`.

До списку електроніки додано замовлення №11 із кількістю 0. Воно навмисно некоректне: програма виводить повідомлення про помилку та продовжує працювати.

`electronics-thread` і `clothing-thread` запускаються через `start()`. Кожен потік перевіряє свої замовлення, виводить результат і зберігає лише успішні замовлення. Метод `join()` очікує завершення обох потоків.

Наприкінці має бути `Збережено замовлень: 10`, загальна сума та список збережених замовлень електроніки. Назви, ціни та кількість генеруються випадково. Порядок повідомлень двох потоків може відрізнятися між запусками.

Після закриття програми замовлення зникають: зберігання реалізоване звичайним списком у пам'яті.

## Модулі

| Maven-модуль | Java-модуль | Призначення |
| --- | --- | --- |
| `order-processing` | `order.processing` | Товари, замовлення, перевірка даних і обробка |
| `order-storage` | `order.storage` | Спільний список замовлень і синхронізований доступ |
| `order-threads` | `order.threads` | JavaFaker, запуск потоків і головний метод |

У кожному модулі є власний `module-info.java`. `requires` визначає залежності, а `exports` відкриває пакети іншим модулям. Пакет `com.example.order.processing.internal` не експортується, тому інші Java-модулі не можуть імпортувати `OrderValidator`.

`requires static lombok` потрібен для компіляції. Після збірки Lombok для запуску не потрібний. У сховищі `requires transitive order.processing` також відкриває залежність на моделі для модулів, які використовують сховище. `order.threads` не експортує свої пакети, а клас `OrderTask` додатково має доступ лише в межах свого пакета.

`requires java.sql` потрібен внутрішній бібліотеці SnakeYAML, яку використовує JavaFaker. Бази даних у цьому проєкті немає.

## Де виконані вимоги

| Вимога | Місце в коді |
| --- | --- |
| Обмежені узагальнення | `Order<T extends Product>`, `OrderProcessor<T extends Product>`, `OrderTask<T extends Product>` |
| Різні типи товарів | `Electronics extends Product`, `Clothing extends Product` |
| Lombok Builder | `@Builder` на конструкторах `Electronics` і `Clothing` |
| JavaFaker | Методи `createElectronicsOrders` і `createClothingOrders` у `Main` |
| Лямбда-вирази | `() -> electronicsTask.run()`, `() -> clothingTask.run()` та `filter(...)` |
| Посилання на методи | `this::processOrder`, `Order::getTotalPrice`, `System.out::println` |
| Обробка винятків | `OrderProcessingException`, перевірки в `OrderValidator`, `try/catch` в `OrderTask` |
| Багатопоточність | Два `Thread`, методи `start()` та `join()` у `Main` |
| Синхронізація | `synchronized` у методах `save` і `getAll` класу `OrderStorage` |
| Модулі та контроль доступу | Три файли `module-info.java`, закритий внутрішній пакет |

## Коротко для захисту

- `Product` — спільний абстрактний клас товару з назвою й ціною. Електроніка додає бренд і гарантію, одяг — розмір і матеріал.
- `T extends Product` дозволяє використовувати лише `Product` або його нащадків. Наприклад, `OrderProcessor<Electronics>` допустимий, а `OrderProcessor<String>` не скомпілюється.
- `@Builder` генерує метод `builder()` і дає змогу створювати товар послідовними викликами `.name(...).price(...).build()`. Анотація стоїть на конструкторі, щоб builder також отримав поля батьківського класу.
- JavaFaker генерує демонстраційні дані. Він працює в головному потоці до запуску обробників.
- `OrderTask<T>` реалізує `Runnable`. Лямбда передає його роботу потоку, а `this::processOrder` викликає обробку кожного замовлення зі списку.
- `start()` запускає окремий потік. Звичайний виклик `run()` виконав би роботу в поточному потоці. `join()` чекає завершення потоку перед підрахунком результатів.
- `synchronized` дозволяє лише одному потоку одночасно виконувати захищений метод на тому самому об'єкті сховища. Обидва потоки використовують один `OrderStorage`. `getAll()` повертає копію списку.
- `OrderProcessingException` — перевірюваний виняток. Обробник оголошує його через `throws`, а задача перехоплює через `catch`, тому неправильне замовлення не зупиняє обробку наступних.
- Обмеження `extends` перевіряє тип під час компіляції, а виняток обробляє неправильні дані під час виконання. Сам клас винятку не є узагальненим: Java не дозволяє узагальнені підкласи `Throwable`.
- Maven-модулі мають окремі `pom.xml` і збираються разом. Java-модулі визначають доступність пакетів через `module-info.java`.

## Тести

Усі 15 тестових перевірок проходять. Вони перевіряють обидва типи товарів, розрахунок суми, некоректні дані, збереження 1000 замовлень двома потоками, захист внутрішнього списку та продовження роботи після помилки. Тестові класи розташовані в `src/test/java` і не входять до основної програми.

Збірку перевірено на JDK 17, запуск готових Java-модулів — на Java 17 і 21. Окремо перевірено, що компілятор відхиляє `OrderProcessor<String>` та імпорт внутрішнього пакета з іншого Java-модуля.
